# ADR-0009: Deterministic English OOV Fallback

## Status

Accepted. Amends ADR-0005 for English word tokens.

## Context

The initial Gofonix OOV behavior was conservative: a word absent from the dictionary could become `SourceUnknown` with no phonemes and zero feature masks. That behavior is deterministic and safe, but it leaves many ordinary English words without any phonological signal when the default mini dictionary is used.

Gofonix needs a fallback that improves coverage without changing the project's core constraints:

- deterministic output;
- no neural or statistical G2P;
- no runtime network access;
- no subprocesses;
- no CGO;
- no public ARPAbet exposure;
- no change to tokenization, alignment, or feature schema semantics.

The `SourceRuleFallback` provenance value exists for exactly this case: a pronunciation that was not found in the dictionary, but was generated by a deterministic rule set.

## Decision

Gofonix uses a deterministic English rule fallback for eligible dictionary-miss word tokens.

The active OOV policy is:

```text
rule-fallback-then-unknown
```

The fallback rule table is identified by:

```text
fallback-en-v0.2
```

Dictionary lookup still takes precedence. Fallback is attempted only after a dictionary miss. If fallback declines the token, the token remains `SourceUnknown`.

## Activation rules

Fallback is attempted only when all of the following are true:

- the token kind is `KindWord`;
- the mode is `ModeBatch` or `ModeOracle`;
- dictionary lookup found no canonical dictionary pronunciation;
- the normalized token contains at least one ASCII letter;
- the normalized token contains no decimal digits;
- every normalized character is an ASCII letter or ASCII apostrophe.

Fallback is not attempted for:

- whitespace;
- punctuation;
- numbers;
- symbols;
- unknown tokens;
- invalid UTF-8 bytes;
- dictionary hits;
- mixed alphanumeric tokens such as `MP3`, `H2O`, `3rd`, and `21st`;
- non-ASCII words such as `café` under the current rule set.

`ModeCausal` remains scaffold-only and does not apply fallback.

## Normalization for fallback

Fallback matching uses a derived key, not the original token bytes.

The normalization steps are:

1. lowercase the token;
2. reject if any decimal digit is present;
3. reject if any character is not `[a-z]` or ASCII apostrophe;
4. remove ASCII apostrophes;
5. reject if the resulting string is empty.

This normalization is only for fallback matching. Token spans and original input bytes remain unchanged.

## Rule representation

Fallback rules are a static, ordered grapheme-to-phoneme table. The right-hand side emits internal ARPAbet-like symbols, but those symbols immediately flow through the existing English ARPAbet-to-neutral-phoneme bridge.

ARPAbet remains internal. Public callers receive only neutral phonemes and feature masks.

The rule table is closed over the existing English phoneme inventory defined by ADR-0008. It must not emit symbols outside that inventory.

## Matching algorithm

The matcher scans the normalized fallback key from left to right.

At each position:

1. find all table graphemes matching at the current position;
2. choose the longest matching grapheme;
3. if there is a same-length tie, choose the alphabetically first grapheme key;
4. append the corresponding internal symbol sequence;
5. advance by the matched grapheme length.

Single-letter rules guarantee progress for accepted inputs. If no rule matches, the whole token is declined and becomes `SourceUnknown`.

The algorithm is deterministic and does not depend on map iteration order, locale, time, randomness, or external state.

## Output semantics

A fallback-resolved token has:

- populated neutral phonemes;
- populated feature masks under `v0.1-en`;
- uniform byte alignment as specified by ADR-0007;
- `SourceRuleFallback`;
- `Variant = 0`;
- `FallbackRulesVersion = "fallback-en-v0.2"`.

Feature projection is identical to dictionary-derived pronunciations. Fallback changes the pronunciation source, not the alignment or feature-stream contract.

If fallback declines, the token has:

- `SourceUnknown`;
- empty phoneme list;
- empty feature list;
- empty alignment;
- zero masks over its byte positions.

## Metadata

The active fallback policy is exposed through result metadata:

- `OOVPolicy = "rule-fallback-then-unknown"`;
- `FallbackRulesVersion = "fallback-en-v0.2"`.

`FallbackRulesVersion` identifies both the rule table and the matching semantics. Any rule-table or matching change requires a new version string.

## Test requirements

The fallback must be covered by tests for:

- activation and decline cases;
- every rule in the frozen table;
- longest-match behavior;
- deterministic tie-breaking;
- multi-symbol output such as `x -> K S`;
- dictionary-hit precedence;
- `SourceRuleFallback` provenance;
- `SourceUnknown` decline behavior;
- alignment and `FeatureStream` projection;
- `ModeCausal` remaining all-zero.

Golden records should include fallback examples so that source, phoneme IDs, alignment spans, feature masks, and metadata are pinned.

## Alternatives considered

### Keep unknown-only behavior

Rejected as the default because it leaves too many ordinary English words without phonological features when using the mini dictionary.

### Neural or statistical G2P

Rejected. It would add complexity, model dependencies, and reproducibility concerns that do not fit the current Gofonix contract.

### Probabilistic or weighted rules

Rejected. The project needs one canonical output for a fixed input.

### Runtime external G2P tools

Rejected. Subprocesses, downloads, and external model dependencies are outside the project constraints.

### Mixed alphanumeric fallback

Deferred. Handling `MP3`, `3rd`, or `H2O` properly requires letter-name, number, and abbreviation policy decisions that are outside this rule set.

## Consequences

- Common English OOV words can receive reproducible phonological features instead of silence.
- Dictionary and fallback pronunciations remain distinguishable by `Source`.
- The rule set is intentionally approximate and must not be presented as linguistically complete.
- Non-ASCII and mixed alphanumeric tokens remain unsupported by fallback.
- The OOV policy is no longer pure unknown-only for English word tokens.
